# ADR-007: Image Studio keeps GRAV file authority while embedding hosted Photopea

- **Decision ID:** ADR-007
- **Date:** 2026-09-21
- **Status:** Approved product direction; implementation details require browser proof
- **Context:** GRAV needs internal image editing without a second file system or manual download/upload. The inspected company drive already owns `Doc_File` records, private Drive bytes, and read/write rules. The user has explicitly allowed hosted Photopea for Image Studio.
- **Decision:** Photopea is the sole planned first editor, behind an `ImageEditorAdapter`/`PhotopeaAdapter` boundary. GRAV remains authoritative for identity, company scope, file permissions, storage, revisions, and save acknowledgment. Embed hosted Photopea through its documented API. Image Studio reuses the drive's server-side `mayRead` / `mayWrite` rules; no separate role framework is introduced. As a conservative disclosure boundary, only unrestricted files the employee may read are eligible for transfer to hosted Photopea; `restricted` and unclassified files are blocked pending explicit approval. Browser-mediated binary messaging is the proposed open/export bridge, subject to end-to-end proof. The backend accepts a Save only after reauthorization, content validation, concurrency control, and durable storage/metadata handling.
- **Alternatives considered:** Self-hosted Photopea (not required for the approved first release; may be revisited for confidentiality or operational control); direct Photopea-to-server save (deferred because authentication, cross-origin access, and acknowledgment do not fit the present drive without more design); signed public URLs (not needed for the proposed browser bridge and risk exposing private data); building a new editor or substituting another suite (outside this product scope); copying the drive into a second Image Studio library (rejected).
- **Consequences:** File bytes enter a third-party-hosted editor in the employee's browser; this must be visible in the product/security documentation. The first release may not be declared complete from mocked messaging alone. Origin/CSP configuration and browser proof are required. Save semantics and revision history must be designed around `Doc_File`; no false success state is allowed. The present drive's broad unrestricted-file write policy remains a known limitation for a separate policy decision. An adapter reduces replacement cost but does not guarantee another editor has identical capabilities.
