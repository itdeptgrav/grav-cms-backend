> **Chunk 2 of the Project Manager professionalisation plan.** Built before any
> guard was changed; the fixes recorded at the bottom follow from it.
>
> **Scope of the search.** Every API string reachable from `app/project-manager/**`,
> from `components/DashboardLayout.js`, from the shared pages the PM shell mounts
> through `AutoDashboardLayout`, and from the components, hooks and libraries
> those import transitively — plus the Socket.IO channels the PM production
> screens join.

> searching `grav-cms`, which holds every department's browser UI. The other
> consumers named in the backend's CLAUDE.md — `grav-CoworkSpace`, the customer
> and vendor portals, and the Expo mobile app — are **not cloned on this
> machine**, so "no other consumer" below means "no other consumer in
> `grav-cms`". Those repos talk to `/cowork/**`, `/api/customer/**`,
> `/api/vendor/**` and `/api/employee/**`; none of the endpoints below sit under
> those prefixes, which is evidence but not proof.

## 2. How to read the middleware column

Three things stack, and they are not the same question:

1. **`router.use(EmployeeAuthMiddleware)`** — *are you signed in.* Inside the
   router file. `Middlewear/EmployeeAuthMiddlewear.js`.
2. **`departmentWrites(slug)`** at the `server.js` mount — *may you write here.*
   `Middlewear/departmentWriteGuard.js:124`. **Never touches GET/HEAD/OPTIONS**,
   and skips POSTs whose path contains a `READ_SHAPED` fragment
   (`/search`, `/export`, `/refresh`, `/check`, … — `departmentWriteGuard.js:93`).
3. **`requireApproval(slug)`** — *does your write need a second pair of eyes.*
   `services/changeRequests.js:181`. Approver/owner commit directly; an editor
   gets 202 and a `ChangeRequest`.

Both (2) and (3) **fail open for a department with no roles configured**
(`services/departmentRoles.js:212`, `services/changeRequests.js:201`). That is a
deliberate migration decision, documented there, and this chunk preserves it.

The load-bearing consequence, and the source of two findings below:
`departmentWrites` passes an anonymous caller straight through on purpose —
*"let the router's own auth middleware refuse it"*
(`departmentWriteGuard.js:160`). **A mount guard is not authentication.** Where
the router had no authentication of its own, there was none at all.

## 5. Findings fixed in this chunk

### 5.1 `MISSING_AUTHENTICATION` — production dashboard (7 endpoints)

**`routes/CMS_Routes/Production/Dashboard/productionDashboardRoutes.js`**

`EmployeeAuthMiddleware` is required on line 5 and was **never installed**. The
`server.js:1631` mount does not compensate: `pmWrites` ignores GET entirely, and
the single POST (`/operations/refresh-cache`) contains `/refresh`, which is on
`READ_SHAPED`, so it was waved through too.

Reachable with no session: `GET /operations`, `/machine-status`,
`/current-production`, `/all-machines`, `/employees-today`, `/find-piece`, and
`POST /operations/refresh-cache`. Between them these return machine assignments,
live production by machine, who is on the floor today, and — via `/find-piece` —
a barcode lookup naming the customer order a garment belongs to.

**Consumers, both authenticated, neither public:**
- Project Manager — `productionStats/page.js:103,123`, `FindPieceModal.js:53`
- Production Supervisor — `tracker/page.js:62,77,92`, `AssignOperationsPanel.js`

Both send `credentials: "include"`. No public consumer exists, so the fix is safe.

**Fix:** `router.use(EmployeeAuthMiddleware)` at the router boundary.
**Authentication only** — the Production Supervisor holds no `project-manager`
role, and gating these reads on a department would break the floor to fix a
login check. URLs and response shapes unchanged.

### 5.2 `MISSING_AUTHENTICATION` — canvas layout (3 endpoints)

**`routes/CMS_Routes/Production/Dashboard/canvasLayoutRoutes.js`**

The identical omission one folder over — required on line 5, never installed —
and more serious, because this router has `POST /` and `DELETE /`.
`productionSupervisorWrites` at `server.js:1648` passes an anonymous caller

**The factory's machine layout could be rewritten or deleted with no session.**
Proven anonymously in `pm-access-boundary.route.test.js` before the fix.

**Consumers, both authenticated:** PM `MachinePositionDesigner.js:84,455` and
`ProductionCanvas.js:142`; Production Supervisor `MachinePositionDesigner.js:67,365`
and `ProductionCanvas.js:114`.

**Fix:** `router.use(EmployeeAuthMiddleware)`. Authentication only — the layout
belongs to the Production Supervisor's floor and the existing

### 5.3 `PM_OWNED_MUTATION` — share to vendor

**`POST /api/cms/manufacturing/manufacturing-orders/share-to-vendor`**
(`manufacturingOrderRoutes.js:1151`)

The only mutation on a PM screen that is **all three** of: unambiguously a
Project Manager business decision (forwarding production to an outside vendor);
called from nowhere else in `grav-cms`; and **replay-safe** — one
`WorkOrder.updateMany` with `$set`, whose filter excludes work orders already
`forwarded`, `completed` or `cancelled`. No stock movement, no notification, no
email, no second write. A replayed approval re-applies the same `$set`; a second
replay matches nothing and returns 400 rather than forwarding twice.

**Fix:** `departmentWrites("project-manager")` applied **as route middleware on
this one handler**, not as a mount. Reuses the existing mechanism — there is no
second role or approval system. Viewer refused; editor held at 202 with a
replayable `ChangeRequest`; approver/owner direct; platform admin direct.

**One local deviation, deliberate.** `requireApproval` exempts platform admins
(`changeRequests.js:197`) but `requireDepartmentRole` ahead of it has no such
check, so an administrator with no Production `DepartmentRole` row would be
refused `NO_DEPARTMENT_ROLE` before the exemption was reached. That asymmetry is
in the shared guard and is **left there** — changing it would change every
department that mounts `departmentWrites`. It is handled in the local wrapper
instead, where the blast radius is one route. Recorded here as a finding worth a
platform-level decision.

### 5.4 Audit (Phase E)

A held change already leaves a `ChangeRequest` plus a submission entry
(`changeRequests.js:280`). A **direct** approver/owner write left nothing: the
`auditTrail` floor is mounted on `/api/hr` and `/api/employees` only
(`server.js:1055-1066`) — there is none under `/api/cms/manufacturing`.

`share-to-vendor` now calls `recordChange` (`services/changeLog.js:267`) — the
established mechanism, not a second one — recording actor, vendor, the work-order
numbers moved, and the resulting status. It is fire-and-forget and cannot cost
the caller their write. **The request body, headers and token are never logged.**

**Gap, documented rather than papered over:** authentication and authorisation
*refusals* are still not recorded anywhere. `requireDepartmentRole` and
`EmployeeAuthMiddleware` return without logging, and the natural place to fix
that is those shared guards, which serve every department. Adding a
PM-only refusal log would be the second audit system this chunk is forbidden to
create. Recommended as a platform-level change, not made here.

## 6. Legacy `ProjectManager` accounts — proposed, not approved

**How tokens are issued.** `routes/login.js:48` probes the `projectmanagers`
collection second in its waterfall. On a bcrypt match it signs
`{ id, role: "project_manager", employeeId, userType: "project_manager", name, email }`
(`login.js:123-135`) — **no `deptSlug`, no `isAdmin`, no `v: 2`, no `subject`.**

**How they reach PM routes.** Identically to any other employee:
`EmployeeAuthMiddleware` verifies the signature and copies the claims onto
`req.user`, with `deptSlug: decoded.deptSlug || null` — always null for these.
Route handlers that only need a signed-in employee accept them.

**Do they have `DepartmentRole` rows?** **No, and nothing creates one.**
`DepartmentRole` is keyed on email and written only by the CEO's Access Control
screen. A legacy `ProjectManager` document is not an `Employee`, so it is
invisible to that screen's roster.

**How `departmentWrites` treats them.** While Production has no roles, the guard
fails open and they write exactly as today. **The moment an administrator grants
the first Production role, every legacy account is refused
`403 NO_DEPARTMENT_ROLE`** — its `role: "project_manager"` claim buys nothing,
because the guards read `DepartmentRole`, never the token role. Pinned as a test
("a legacy ProjectManager session is treated by its DepartmentRole, not its
token role") so this is a known cliff rather than a surprise.

**How platform admins differ.** `isAdmin` is minted only by the v2 path in
`routes/auth/deptAuth.js`; the legacy waterfall never sets it. A legacy account
can therefore never be an admin, and never take the admin exemption.

**What would break if legacy accounts were removed today.** Anyone whose only
credential is a `projectmanagers` row loses sign-in outright — `login.js` would
fall through to the next collection and return "invalid credentials". Nothing
else references the model: no route imports it except `login.js:21,217`, and no
record foreign-keys to it. (`test/store-purchase/deliveries-returns.route.test.js:17`
requires it only to register the schema.)

**Recommended migration (proposed).**
1. Report which `projectmanagers` rows are still active and whether an
   `Employee` exists with the same email.
2. For each, create the `Employee` if missing, then grant the intended
   Production `DepartmentRole`.
3. **Grant the roles before turning on enforcement** — the fail-open window is
   the only thing preventing a lockout today.
4. Keep the legacy login path for one token lifetime (7 days) after the last
   legacy sign-in, then remove the probe from `login.js` and retire the model.
5. Do not delete `models/ProjectManager.js` before step 4 completes.

**Status: proposed. Not approved, not implemented.** Nothing in this chunk
deletes, migrates or alters the model.

## 7. Left unchanged, with reasons

### 7.1 Unsafe to put through the generic approval queue

`requireApproval` holds a request and replays it later. That is only sound for a
mutation that can be applied twice, or not at all, without harm. These cannot
be, so per the chunk's own rule they keep **exactly** their current behaviour
and are marked `UNKNOWN_REQUIRES_DECISION`:

| Endpoint | Why replay is unsafe |
|---|---|
| `PUT /work-orders/:id/allocate-raw-materials` (`workOrderRoutes.js:739`) | Consumes raw stock, and `splitRemaining` splits the work order in two. A replay allocates twice and splits twice. |
| `PUT /work-orders/:id/plan-operations` (`:914`) | Rewrites the operation set; a delayed replay overwrites planning done since. |
| `POST /work-orders/:id/complete-planning` (`:1003`) | State transition to `scheduled`; replaying against a moved-on work order re-scheds it. |
| `POST /work-orders/:id/start-production` (`:1043`) | Guarded on current status — a replay after the floor started is meaningless. |
| `POST /work-orders/bulk-plan` (`:1172`) | Fans out across many work orders; partial application on replay is unrepresentable in one ChangeRequest. |
| `POST /work-orders/:id/operations`, `DELETE /:id/operations/batch`, `DELETE /:id/operations/:operationId`, `PUT /:id/operations/reorder` (`:1089`, `:1111`, `:1134`, `:1151`) | Order-sensitive edits to a list; replay out of sequence corrupts it. |
| `POST /manufacturing-orders/:id/work-orders/:woId/mark-stage` (`:1557`) | **Not idempotent — because of its dispatch stage.** Production, QC and packaging apply `quantity` as a capped target, so an identical repeat of those adds nothing; **dispatch applies it as an additional amount** (`min(quantity, packaged − alreadyDispatched)`), so a delayed replay dispatches further units. It also appends to the `ProductionCompletionScanRecord` ledger the barcode floor writes, and is **not PM-exclusive at the record level**. (This is *not* the disproven "a replay double-counts production" claim — see the lifecycle decision §9.3.) |

Each also fails the *ownership* test to some degree — the floor writes the same
records — which is the second reason not to gate them on `project-manager`.

### 7.2 Missing authentication outside this chunk's blast radius

Found by this inventory, **evidenced, and deliberately not fixed here** because
each is owned by another department and its consumers could not be verified
without those repos:

| Router | Mount | Finding |
|---|---|---|

| `Manufacturing/Embroidery/embroideryRoutes.js` | `server.js:1515` | No auth import at all. `MISSING_AUTHENTICATION`. |

Fixing these needs the same consumer proof that made §5.1 and §5.2 safe, and

### 7.3 Deliberately not gated on `project-manager`

## 8. Reproducing the inventory

The endpoint list is mechanical, so it can be regenerated and diffed rather than
trusted. From the frontend repository root:

```bash
{
  grep -rhoE "/api/[a-zA-Z0-9/_.\$\{\}-]+" app/project-manager
  grep -rhoE "/api/[a-zA-Z0-9/_.\$\{\}-]+" \
    app/sales/dashboard/stock-items \
    app/sales/dashboard/size-config \
    app/sales/dashboard/inventory-configurations
  grep -rhoE "/api/[a-zA-Z0-9/_.\$\{\}-]+" lib/salesJourney app/sales/dashboard/journeys
  grep -rhoE "/api/[a-zA-Z0-9/_.\$\{\}-]+" \
    components/access components/DashboardLayout.js \
    lib/pushNotifications.js lib/session.js lib/signOut.js lib/changeRequests.js
} | sed -E 's/\$\{[^}]*\}/:param/g' | sed 's/[?`"'"'"'].*$//' | sed 's|/$||' \
  | grep -vE '\$\{|\.$' | sort -u
```

The four groups are, in order: the Project Manager subtree; the shared pages the
PM shell re-exports (Products & BOM, size config, the four inventory
configuration screens); the Sales Journey the Pipeline reuses; and the shell,
access, notification and change-request helpers every PM page loads.

To re-check which routers authenticate, from the backend root:

```bash
grep -n "router.use(EmployeeAuth" routes/CMS_Routes/**/*.js
```

A router that `require`s an auth middleware without a matching `router.use` is
the shape of both findings in §5 and all three in §7.2.
